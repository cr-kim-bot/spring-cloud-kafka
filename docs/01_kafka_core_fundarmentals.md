# Kafka Cluster

- 여러개의 kafka 노드를 묶는 그룹
- 고가용성 확보: 단일 노드에 문제가 생겨도 어플리케이션에 영향을 미치지 않는다.
- 수평 확장성: 어플리케이션은 kafka 단일 노드와 통신을 하게 되고 부하 분산을 위해 여러개의 kafka 노드를 운영한다.
- kafka 노드들끼리 동신을 한다.

# Kafka Node Role

1. 브로커
   - 데이터의 관리 및 저장을 담당
   - 읽기 및 쓰기 요청을 처리 (Producer/Consumer와 통신)
   - 클러스터 내에 여러 브로커를 배치할 수 있다.
2. 컨트롤러
   - 클러스터를 관리하는 역할을 담당
   - 노드 관리
   - 클러스터 내에서는 하나의 액티브 컨트롤러만 존재
   - 컨트롤러는 클라이언트와 통신하지 않음
   - 컨트롤러가 장애가 나면 다른 노드줄에서 컨트롤러를 선출
   - `process.roles` 속성을 통해 역할 지정 `broker` `controller` `broker,controller`

# process.roles 상세

| 값 | 설명 |
|---|---|
| `broker` | 브로커 역할만 수행, 컨트롤러 선출 대상에서 제외 |
| `controller` | 컨트롤러 역할만 수행, 브로커 역할 없음 |
| `broker,controller` | 브로커 역할 수행 + 컨트롤러 선출 대상 포함 |

## 대규모 클러스터 (100개 이상 노드)

- 컨트롤러가 해야 할 작업이 많아 **전용 컨트롤러 노드**를 별도로 지정
- 보통 3~5개 노드를 `process.roles=controller`로 설정
- 이 중 하나가 액티브 컨트롤러, 나머지는 스탠바이 노드로 대기
- 나머지 노드는 `process.roles=broker`로 설정

## 소규모 클러스터

- 전용 컨트롤러를 두면 해당 머신이 대부분 유휴 상태 → 비효율
- 모든 노드를 `process.roles=broker,controller`로 설정
- 모든 노드가 브로커이면서 컨트롤러 선출 대상이 됨
- 액티브 컨트롤러가 죽으면 나머지 노드 중 하나가 새 컨트롤러로 선출

> 컨트롤러 선출에는 `controller` 속성이 포함된 노드만 참여 가능

# Kafka 설정 파일

Kafka 컨테이너 기준 `/opt/kafka/config/` 경로에 아래 파일들이 존재

| 파일 | process.roles 값 | 용도 |
|---|---|---|
| `broker.properties` | `broker` | 브로커 전용 노드 설정 |
| `controller.properties` | `controller` | 컨트롤러 전용 노드 설정 |
| `server.properties` | `broker,controller` | 단일/소규모 클러스터 기본 설정 |

- Kafka 서버 시작 시 `bin/kafka-server-start.sh` 에 설정 파일을 인자로 전달
- Docker 컨테이너 기본값은 `server.properties` → `broker,controller`

> 이 내용은 Kafka 내부 동작 방식이며, 애플리케이션 개발 코드에는 영향 없음
> 클러스터가 1개든 100개든 애플리케이션 코드는 동일

# Topic과 브로커 할당

- 토픽 생성 시 컨트롤러가 특정 브로커를 지정하여 해당 토픽의 소유권 부여
- 지정된 브로커가 해당 토픽의 읽기/쓰기 요청을 전담 처리
- Producer → 브로커에 메시지 저장 (디스크), Consumer → 브로커에서 메시지 수신

## 단일 브로커의 문제점

- 담당 브로커가 죽으면 해당 머신 디스크의 데이터도 함께 유실
- 데이터 손실 + 서비스 중단 → 프로덕션 환경에서 허용 불가

# 복제 (Replication)

- 컨트롤러가 리더 브로커를 지정할 때 함께 **팔로워 브로커**도 지정
- 리더는 메시지를 수신하면 디스크에 저장하고, 팔로워들에게도 동일한 데이터를 복제
- 리더가 죽으면 팔로워 중 하나가 즉시 새 리더로 승격 → 서비스 무중단 유지

## 리더 / 팔로워 용어

| 용어 | 역할 |
|---|---|
| 리더 (Leader) | 읽기/쓰기를 담당하는 주 브로커 |
| 팔로워 (Follower) | 리더로부터 데이터를 복제받는 백업 브로커 |

> 리더가 죽으면 팔로워 중 하나가 새 리더로 선출됨

## 다중 토픽 분산

- 토픽마다 리더/팔로워가 독립적으로 지정됨
- 예: `order-events` 리더 → 브로커A, 팔로워 → 브로커B·C
- 예: `payment-events` 리더 → 브로커B, 팔로워 → 브로커A·C
- 데이터가 클러스터 전체에 분산되어 부하도 함께 분산

# 정리

| 구분 | 개발 환경 | 프로덕션 환경 |
|---|---|---|
| 구성 | 단일 노드 | 클러스터 (다중 노드) |
| 목적 | 빠른 셋업 | 고가용성 + 수평 확장 |

- 클러스터 내 역할: 브로커 (읽기/쓰기), 컨트롤러 (클러스터 관리), 또는 둘 다
- 액티브 컨트롤러는 항상 1개, 장애 시 다른 컨트롤러 후보가 즉시 인계
- 리더 브로커 장애 시 팔로워가 즉시 리더로 승격
- 단일 장애점(SPOF) 없음 → 애플리케이션 코드 변경 없이 무중단 운영 가능

# Bootstrap Server

- 클러스터에 수백~수천 개의 노드가 있을 때, 애플리케이션이 어떤 브로커에 연결해야 할지 알 수 없는 문제를 해결
- **단 하나의 브로커 IP만 알면 됨** → 해당 브로커가 전체 클러스터 메타데이터를 애플리케이션에 전달
  - 어느 브로커가 어떤 토픽을 갖고 있는지 등 클러스터 전체 정보 제공
- 메타데이터 수집 및 관리 코드는 Kafka 공식 클라이언트 라이브러리가 내부적으로 처리 (직접 구현 불필요)
- 특별한 역할이 아니며, **어떤 브로커든 bootstrap server 역할 수행 가능**

## 고가용성을 위한 다중 Bootstrap Server 설정

- bootstrap server로 지정한 단일 노드가 다운되면 애플리케이션이 클러스터에 접근 불가
- 해결책: `application.properties`에 여러 브로커를 리스트로 지정

```properties
spring.kafka.bootstrap-servers=broker1:9092,broker2:9092,broker3:9092
```

- 리스트 중 하나에만 연결되면 나머지 클러스터 정보는 자동으로 획득

# Log Retention Policy

Kafka는 데이터를 디스크에 저장하며, 보존 기간은 **브로커 레벨 속성**으로 제어한다 (`server.properties`).

## 보존 방식

두 조건을 모두 적용하며, **먼저 충족되는 조건**에 따라 오래된 데이터를 삭제한다.

| 속성 | 기본값 | 설명 |
|---|---|---|
| `log.retention.hours` | `168` (7일) | 지정 시간이 지난 메시지 삭제 |
| `log.retention.bytes` | `-1` (무제한) | 토픽 크기가 지정 바이트를 초과하면 삭제 |

## 백그라운드 정리

Kafka는 주기적으로 메시지를 확인하여 보존 조건을 초과한 데이터를 삭제한다.

| 속성 | 기본값 | 설명 |
|---|---|---|
| `log.retention.check.interval.ms` | `300000` (5분) | 정리 작업 실행 주기 |

> 보존 정책은 토픽 단위로도 오버라이드 가능하다.
